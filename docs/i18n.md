# Localization

Fleet ships two interface languages: English and Simplified Chinese. This note
records what that means in the code, why it is built the way it is, and what is
still English. Every claim about how software _should_ do this is sourced at the
bottom rather than asserted.

## Where the switch is

`Settings > General > Language` is the first row on the General page, and the
default is `Follow System`, which reads the OS locale. The same three choices are
also in the command palette (`Cmd+K`, then "language"), because a preference you
set once is only findable if you can search for it.

## How it is built

A per-app language preference is the shape the platform vendors settled on:
Android 13 added system-level per-app language settings driven by
`LocaleManager.setApplicationLocales`, and Material's writing guidance assumes
the product, not the OS, owns the choice.

> "The public APIs, such as the setApplicationLocales and getApplicationLocales methods in LocaleManager, let apps set a different language from the system language at runtime." … "These APIs automatically sync with system settings"
> — Android Developers, _Per-app language preferences_

| Piece                  | File                                    | What it does                                               |
| ---------------------- | --------------------------------------- | ---------------------------------------------------------- |
| Catalogues             | `src/shared/i18n/en.ts`, `zh-Hans.ts`   | Flat `surface.thing` keys, `{placeholders}` for values     |
| Entry point            | `src/shared/i18n/index.ts`              | `resolveLocale` picks a locale; `translate` looks a key up |
| Renderer hook          | `src/renderer/src/lib/i18n.ts`          | `useTranslation()`, `useLocale()`, `useDocumentLanguage()` |
| Setting                | `FleetSettings.general.language`        | `'system' \| 'en' \| 'zh-Hans'`                            |
| Dates and elapsed time | `src/renderer/src/lib/relative-time.ts` | `formatDateTime` (Intl) and `formatElapsed`                |

The English catalogue defines `MessageKey`; the Chinese one is typed
`Record<MessageKey, string>`. A key that is not translated is a compile error,
not a silent fallback to English.

## The decisions

### Declare the language of the document

`<html lang>` is set from the active locale and kept in step by
`useDocumentLanguage()`. It is not decoration: the W3C lists font choice,
line breaking, hyphenation, spell checking, quote-mark styling, font selection
for Han characters whose shapes differ between Chinese and Japanese, and speech
synthesis among the things user agents key off it. Apple's text engine and its
speech voices are documented to consult the same signal.

> "Always use a language attribute on the `html` tag to declare the default language of the text in the page."
> — W3C, _Declaring language in HTML_

> "User-agents can (and do) use language information to select language-appropriate fonts."
> — W3C, _Why use the language attribute?_

> "used to select localized glyphs (if supported by the font), and locale-specific line-breaking rules."
> — Apple, _Core Text: kCTLanguageAttributeName_

> "The language of a voice controls the conversion of text to spoken phonemes." … "For best results, ensure that the language of an utterance's text matches the voice for the utterance."
> — Apple, _AVSpeechSynthesisVoice.language_

An interface that renders Chinese inside `<html lang="en">` therefore gets the
wrong Han glyphs and is read aloud with English phonetics.

### Locale ids name a script, not a country

The Chinese locale is `zh-Hans`, not `zh-CN`. What ships is a script, and the
BCP 47 script subtag says so instead of leaving a region to imply it. This is
also the convention the Android documentation uses for its own pages:
`developer.android.com` serves its localization article with
`hreflang="zh-Hans"`.

`resolveLocale` maps _any_ Chinese system locale (`zh`, `zh-Hans-CN`, `zh-TW`) to
it. A Traditional reader is better served by Simplified than by nothing.

### The UI font stack has to be able to draw Han characters

`--font-sans` in `src/renderer/src/index.css` is
`'Inter', 'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', 'Noto Sans CJK SC', ui-sans-serif, system-ui, sans-serif`.

Inter carries Latin and digits and has **no** Han glyphs. Without named CJK faces
after it, a Chinese tab title falls through to whatever the OS offers first, and
on macOS that can be a Japanese-first face, which draws characters like 直 and 骨
with the wrong shapes. Naming the Chinese faces before the generic stack, and
declaring `lang`, are the two halves of the same fix.

Apple's rationale for reaching for the system font in the first place is the
same one: the system families are the ones with the language coverage.

> "Apple provides two typeface families that support an extensive range of weights, sizes, styles, and languages."
> — Apple, _Human Interface Guidelines: Typography_

> "the system follows this list to pick a fallback font that includes the character."
> — Apple, _Core Text: CTFontCopyDefaultCascadeListForLanguages_

> "Enabled previous elements with `lang=` to affect fonts selected for subsequent elements"
> — Apple, _Safari Technology Preview release notes_

### Dates go through `Intl` with the locale passed in

`formatDateTime(stamp, locale)` takes the locale explicitly. `toLocaleDateString()`
with no argument reads the _browser's_ locale, so someone who picks English on a
Chinese Mac would read `8月12日` inside an English list.

> "make sure to specify that language (and possibly some fallback languages) using the `locales` argument."
> — MDN, _Intl.DateTimeFormat_

### Elapsed time is a compact template, deliberately

`formatElapsed` is `just now / 5m ago / 5h ago / 5d ago` from the catalogue,
not `Intl.RelativeTimeFormat`.

This is the one place this codebase knowingly does not use the locale-aware API.
`Intl.RelativeTimeFormat` is right for prose, and its `narrow` style still spells
out "5 min. ago" — which does not fit a sidebar chip that competes with the title
it describes. Both shipped locales are safe with a template: English abbreviates
a unit that does not inflect, and Chinese has no plural form. A third locale that
inflects, or one with more than two plural categories, would make this the wrong
call, and `formatElapsed` is the single place to change.

Absolute timestamps in the same rows _do_ use `Intl`, because there the locale's
own date order and month names are the point.

> "US English uses month-day-year order" … "Korean uses year-month-day order."
> — MDN, _Intl.DateTimeFormat_

> "this needs plural forms."
> — Unicode CLDR, _LDML Part 4: Calendar Fields_

### Words live in one place, not in templates

Strings are whole sentences with named placeholders (`{count} tabs`), never
concatenated fragments. This is what Android's resource documentation asks for,
and Apple's SwiftUI documentation reaches for interpolation when a string has to
be composed.

> "If you need to format your strings, then you can do so by putting your format arguments in the string resource"
> — Android Developers, _String resources: Formatting strings_

> "When composing a complex string, where there is a need to assemble multiple pieces of text, use string interpolation."
> — Apple, _SwiftUI: Text, Localizing strings_

The one place fragments are still assembled is the agent settings panel, which is
not translated yet — see below. That is also why it is not half-translated.

### Native chrome is translated in the main process

A terminal pane's right-click menu is an Electron `Menu`, and the window title
and desktop notification are drawn by macOS and Notification Center. No renderer
component can see or relabel them, so the main process resolves the same
`FleetSettings.general.language` preference through the same
`resolveLocale` + `translate` pair and builds those labels itself.

That is where the catalogue's `...One` / `...Other` pairs earn their keep: the
window title and the notification body count agents, and the old
`error${n > 1 ? 's' : ''}` trick is an English-only rule wearing a template. The
pair keeps the inflection in the language file, where the `formatElapsed` note
above already says it belongs.

### Leave room for text to grow

Every label on the sidebar and the settings rail was measured in both languages
for clipped text (`scrollWidth > clientWidth`) as part of the QA pass, and none
clip. Chinese is usually shorter than English, so that measurement says nothing
about the _next_ locale. Material's number for that case is 1.5x, and its
truncation rule is that growth must not silently lose content. Microsoft's
checklist adds the technique — pseudolocalization — for finding the damage
automatically.

> "Other languages average at 1.5 times longer than English, so text that's short may be long when translated."
> — Material Design 3, _Global writing_

> "Increased size of text, increased spacing between text, and translation into longer languages shouldn't result in losing content."
> — Material Design 3, _Writing: Text truncation_

> "English strings often expand by 40% when translated into German or Dutch."
> — Microsoft, _Windows Internationalization Checklist_ (vendor guidance)

Practical reading: assume a third to a half longer than English, and when a new
locale lands, re-run the clipping probe rather than trusting the current
screenshots.

Apple states the same requirement as a layout rule, which is the one to apply
when a label does grow:

> "containers may need to grow in height so that text isn't cropped or doesn't overlap"
> — Apple, _Human Interface Guidelines: Layout_

> "Support Dynamic Type by adjusting your layout to accommodate text at larger sizes."
> — Apple, _Human Interface Guidelines: Layout_

## What is still English

Everything the app renders itself is translated: the shell and its lists, the
command palette and the shortcuts overlay, every Settings page, the agent pane
and its cards, the SSH browser, the file, notes, `.env`, session, git and tool
dialogs, and the native menus, window title and notifications that only the main
process can build.

What stays English is what Fleet did not author:

1. Text that arrives at runtime - model output, MCP and skill descriptions, tool
   names and summaries, and error strings from SFTP, the updater and
   third-party APIs. Translating those means inventing a second copy of somebody
   else's words, and the copy would be wrong the moment the sender changes.
2. Identifier-shaped strings: model ids, JSON keys, environment variables,
   commands, file paths, URLs, and the language names in
   `src/shared/languages.ts`, which are matched against file extensions.
3. Release notes, in the Updates page and the "What's new" dialog. They are the
   project's own record of what changed, closer to a commit message than to
   interface copy, and they are written once in the language the project works
   in.
4. Placeholder examples that demonstrate a syntax rather than say anything, such
   as `API_KEY=…` in the MCP header field.

The Language row's hint says the runtime half of this out loud, because a reader
who sees an English tool description inside a Chinese interface should not
conclude the setting is broken.

## Adding a third locale

1. Add `<locale>.ts` typed `Record<MessageKey, string>`; the compiler lists every
   key you have not translated.
2. Add it to `LOCALES` and `CATALOGUES`.
3. Add an option to the picker and a palette command.
4. Re-read the `formatElapsed` note above: a locale with real plural rules is the
   signal to move that function onto `Intl.RelativeTimeFormat`.

## Where Apple and Material do not speak

Two things worth recording as _absent_ rather than inferred:

- Apple's HIG no longer has a dedicated localization page — the old
  `human-interface-guidelines/localization` URL 404s. What it has instead is
  `Inclusion > Languages`, `Writing`, `Typography` and `Layout`, which are what
  this note cites.
- Neither Apple's HIG nor Material states the text-expansion guidance as a
  standard. Apple lists "Dynamic Type may cause translation to be cut off" as an
  area still needing guidance in its current HIG; Material's 1.5x is a design
  heuristic, not a specification.
